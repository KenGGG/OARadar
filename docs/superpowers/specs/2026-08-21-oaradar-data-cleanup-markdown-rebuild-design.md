# OARadar 数据清理与 Markdown 知识库重建设计

日期：2026-08-21  
状态：待用户书面复核  
实施基线：`main@de632fc`

## 1. 目标

本次工作不是继续修补旧 `data/`，而是在旧资料完全保留的前提下，新建一套干净资料库：

1. 保留全部已经核验的 OA 原始事项、正文和附件；
2. 不从 OA 重新下载历史资料，不对 OA 做任何写操作；
3. 删除旧 Markdown、旧解析尝试、隔离区、日志、报表、浏览器缓存和退役功能产物等无关内容；
4. 用当前最新转换方式，从原始资料重新生成 Markdown；
5. 先在 WebUI 完成人工分类确认，再生成正式目录；
6. 每个事项生成 `_index.md`，有发文文号的事项还要生成独立的“正文.md”；
7. 新资料库完整验收后才切换，旧资料库至少只读保留 7 天；
8. 永久删除旧资料前必须再次取得用户明确授权。

本设计取代 `2026-08-19-oaradar-v2-convergence-design.md` 中与本次一次性资料重建冲突的以下限制：不清理旧文件、不重建历史 Markdown、不重新处理已有成功文件。三条日常自动化流水线、OA 只读、原件不可覆盖等其他边界继续有效。

## 2. 最重要的安全原则

不得直接在现有 `data/` 中边删除边重建。

重建期间同时存在：

```text
data/           当前正式资料库，保持可运行、可恢复
data_rebuilt/   新资料库，只写重建结果
```

只有新资料库全部验收通过后，才进行短暂停机切换：

```text
data/           → data_legacy_<日期>/
data_rebuilt/   → data/
```

以下行为始终禁止：

- 修改、审批、回复、删除、转发 OA 事项；
- 为重建历史资料而重新下载 OA；
- 覆盖或删除已核验的原始文件；
- 在校验完成前删除旧 `data/`；
- 把真实 OA 内容、文件名、页面、数据库或运行日志提交到 Git；
- 未经用户再次授权永久删除 `data_legacy_<日期>/`。

## 3. 新资料库保留什么

新资料库只保留系统继续运行和知识库查阅所需内容：

```text
data_rebuilt/
├── archive/       OA原始事项、原始正文和原始附件
├── parse/         每个原始文件最新一次成功转换得到的标准文本和必要图片
├── markdown/      最终给人阅读和给 Obsidian 使用的知识库
├── state/         系统正常运行所需的数据库
└── runtime/       当前运行确实需要的少量临时文件
```

以下旧内容不进入新资料库：

- 旧 Markdown 和旧知识提炼结果；
- 同一原始文件的旧版、失败版和重复解析结果；
- Curated、Vault、Review、治理、在线核验等退役功能的文件产物；
- 旧隔离区、旧报表、旧日志、旧浏览器缓存和过期备份；
- 找不到来源、不能与数据库记录对应或哈希不一致的文件。

不能确认是否有用的文件不得直接删除，统一留在旧资料库等待人工处理。

## 4. 原始资料保护

重建开始前生成一份只读清单。每个原始文件至少记录：

- 所属 OA 事项；
- 原始文件名；
- 当前相对路径；
- 文件大小；
- SHA256；
- 文件角色，例如正文、普通附件或容器内文件；
- 是否真实存在；
- 是否通过完整性检查。

只有真实存在且哈希一致的文件才能复制到新 `archive/`。复制后再次计算哈希，必须与旧文件完全一致。

重建不得改变原始文件内容。数据库继续用文本保存 OA 标识，用相对 `data_root` 的 POSIX 路径保存文件位置。

## 5. 分类确认工作流

正式生成知识库目录前，WebUI 增加“资料重建”页面。页面分为：

```text
内部事项
外部事项
待确认事项
```

每条事项显示：

- 标题；
- 文号；
- 发起人或发文机构；
- 事项日期；
- 建议的内部类型或外部机构；
- 是否需要生成正文；
- 附件数量；
- 当前确认状态。

分类过程分为“系统建议”和“人工确认”两个状态。系统建议不能直接生成正式知识库目录。

### 5.1 内部事项

系统先判断是否属于凯得租赁内部事项，再建议以下一个内容类型：

```text
公司治理
经营管理
业务项目
风险管理
财务资金
人力行政
信息化
其他内部
```

用户可以查看全部标题、修改单条建议，然后一次确认全部明确的内部事项。

### 5.2 外部事项

凯得金服、广开控股，以及区、市、省、国家等外部单位，均按照规范化后的具体机构名称分类，不按照行政层级合并。

例如：

```text
广州市工业和信息化局
广州凯得金融服务集团有限公司
广州开发区控股集团有限公司
```

同一机构的简称、全称和历史写法应先统一为一个名称。用户可以查看全部标题、修改单条建议，然后一次确认全部明确的外部事项。

### 5.3 待确认事项

待确认事项必须逐条处理：

- 选择“内部”时，必须选择一个内部内容类型；
- 选择“外部”时，必须填写或选择具体机构；
- 未确认事项不得进入正式 Markdown 知识库；
- 不为未确认事项创建“待确认”正式目录。

分类修改必须留下本地操作时间和修改前后结果，但不得记录或上传真实正文。

## 6. 日期和目录规则

事项日期按以下顺序选择：

1. 公文落款或成文日期；
2. OA 发起日期；
3. OA 办结日期。

如果三者都不存在，事项不能进入正式目录，必须在 WebUI 显示为“日期待补充”。

月份使用两级时间目录：

```text
2026年/
└── 08月/
```

月份目录下，每个 OA 事项使用独立文件夹：

```text
20260820-文号-事项标题/
```

没有文号时使用：

```text
20260820-事项标题/
```

文件夹名称需要去除文件系统不允许的字符、尾部空格和控制字符。过长标题应确定性截短，并附加 OA 事项标识的短哈希，确保同名事项不会互相覆盖。

## 7. Markdown 目录

### 7.1 内部事项

```text
markdown/
└── 内部事项/
    └── 风险管理/
        └── 2026年/
            └── 08月/
                └── 20260820-文号-事项标题/
```

一级业务目录必须是第 5.1 节列出的固定内容类型之一。

### 7.2 外部事项

```text
markdown/
└── 外部事项/
    └── 广州市工业和信息化局/
        └── 2026年/
            └── 08月/
                └── 20260820-文号-事项标题/
```

外部一级业务目录使用经过人工确认的具体机构名称。

### 7.3 分类变化

人工确认前不创建最终目录。人工确认后如果再次修改分类，系统应先检查目标目录冲突，再整体移动该事项的 Markdown 文件夹并重写内部相对链接。原始 `archive/` 不因分类变化而移动。

## 8. 每个事项包含哪些文件

没有发文文号的事项：

```text
事项文件夹/
├── _index.md
├── 附件一.pdf.md
├── 附件二.xlsx.md
└── assets/
```

有发文文号的事项：

```text
事项文件夹/
├── _index.md
├── 文号-事项标题-正文.md
├── 附件一.pdf.md
├── 附件二.xlsx.md
└── assets/
```

原始附件只在 `archive/` 保存一份。Markdown 使用受保护的相对链接指向原始附件，避免复制第二份原件。如果 Obsidian 实际环境不能可靠打开该链接，验收阶段停止切换并改用复制附件方案。

## 9. 正文规则

“正文.md”只出现在具有发文文号的 OA 事项中。

正文来源按以下顺序选择：

1. OA 数据中明确标记为正文或主文档的附件；
2. 文件名包含“正文”、完整文号或完整事项标题的主文档附件；
3. OA 页面正文。

选为正文的原始附件仍在 `archive/` 中保存，但不再重复生成普通附件 Markdown。

正文文件名固定为：

```text
文号-事项标题-正文.md
```

正文来源不存在或转换失败时，该事项不能标记为重建成功，WebUI 必须显示具体原因并允许重试。系统不得生成空白正文或伪造内容。

## 10. 附件 Markdown 规则

新知识库不复制旧 Markdown 内容。每个支持转换的原始文件都使用当前最新转换程序重新处理：

```text
原始文件
→ 最新解析程序
→ 最新成功标准文本
→ Markdown
```

普通附件 Markdown 使用原文件名追加 `.md`：

```text
预算表.xlsx.md
会议材料.pdf.md
```

一个附件失败不得撤销其他附件已经成功的结果。暂不支持的格式保留原始文件，并在 `_index.md` 中明确写出“暂不支持转换”。可转换文件失败时显示“转换失败，等待重试”。

每个原始文件只保留最新一次成功标准文本和它实际引用的图片等资源。失败尝试和旧版本不进入新资料库。

## 11. `_index.md` 规则

每个已确认事项必须且只能有一个 `_index.md`。内容包括：

- 标题；
- 文号；
- 发起人或发文机构；
- 成文、发起和办结时间；
- 内部或外部；
- 内部内容类型或外部具体机构；
- 正文链接，仅有文号事项显示；
- 原始附件清单及受保护链接；
- 成功附件 Markdown 链接；
- 暂不支持或转换失败的附件状态。

分类信息同时写入 `_index.md` 和正文、附件 Markdown 的开头，便于 Obsidian 按目录、标题、文号、类别和机构搜索。

## 12. 重建执行流程

### 阶段 A：只读盘点

- 暂不暂停日常服务；
- 统计原始事项、文件、正文候选、分类建议和磁盘空间；
- 生成不包含真实正文的本地清单；
- 检查新旧资料库同时存在所需空间；
- 空间不足或发现原件缺失时停止，不进入复制阶段。

### 阶段 B：WebUI 分类确认

- 展示内部、外部、待确认三组；
- 支持修改单条建议；
- 支持整批确认明确的内部和外部事项；
- 待确认事项逐条处理；
- 记录本次重建采用的分类结果；
- 未全部处理的事项不进入正式输出。

### 阶段 C：建立 `data_rebuilt/`

- 建立干净目录；
- 复制已核验原始文件；
- 复制后逐个复核 SHA256；
- 复制系统运行需要的数据库事实；
- 不复制旧派生文件和退役产物。

### 阶段 D：重建知识库

- 按已确认分类逐项执行；
- 使用现有任务与重试机制记录进度，不新增第三套日常 Worker；
- 支持中断后继续；
- 生成最新标准文本、正文、附件 Markdown 和 `_index.md`；
- 每完成一项立即校验文件和链接。

### 阶段 E：补齐增量并验收

- 记录初始盘点时间；
- 切换前暂停 Web、OA Worker、Markdown Worker 和 timers；
- 补齐盘点以后新增或变化的已办事项；
- 对复制的数据库做一致性检查；
- 执行第 13 节的全部验收。

### 阶段 F：切换

- 将旧目录改名为 `data_legacy_<日期>/`；
- 将 `data_rebuilt/` 改名为 `data/`；
- 更新必要配置并启动服务；
- 核验 WebUI、Worker、定时任务、Markdown 和本地目录；
- 切换失败时立即停服务并恢复旧目录，不删除任何业务数据。

## 13. 验收标准

切换前必须全部满足：

1. 旧库所有已核验原始文件都在新库存在；
2. 新旧原始文件 SHA256 逐个一致；
3. 没有来源不明或哈希不符文件混入新库；
4. 所有正式输出事项都已经人工确认分类；
5. 每个正式事项恰好一个 `_index.md`；
6. 每个有文号事项恰好一个“文号-事项标题-正文.md”；
7. 无文号事项没有“正文.md”；
8. 所有支持转换的普通附件都有成功 Markdown，或有明确可重试失败；
9. 所有不支持转换的附件在 `_index.md` 中明确标记；
10. 所有 Markdown 内部链接和原始附件链接有效；
11. WebUI 能按内部、外部、机构、类型、年份和月份查询；
12. Obsidian 能按目录、标题、文号、类型和机构查找；
13. 随机抽查至少 100 个内部事项和 100 个外部事项；
14. 新库不包含旧日志、旧报表、浏览器缓存、旧隔离区和退役知识产物；
15. 自动测试、前端检查、构建和本机服务冒烟全部通过。

任何一项不满足，都不得切换正式目录。

## 14. 切换后的观察和删除

切换后先观察 24 小时，再连续观察 7 天。观察内容包括：

- 新已办事项能进入正确目录；
- 新有文号事项能生成正文；
- 新附件能生成 Markdown；
- 分类修改不会丢文件或破坏链接；
- WebUI 和 Obsidian 能正常打开资料；
- 原始附件没有缺失或被覆盖。

观察通过后只生成“旧目录拟删除清单”，列出文件类别、数量和空间占用。永久删除 `data_legacy_<日期>/` 必须再次取得用户明确授权。Git 标签、远程分支和数据库历史清理不包含在本次删除授权中。

## 15. WebUI 边界

“资料重建”页面只提供本次任务需要的功能：

- 查看盘点数量和完整性；
- 查看内部、外部、待确认事项；
- 修改并确认分类；
- 查看正文来源；
- 启动、暂停和继续重建；
- 查看成功、失败和剩余数量；
- 查看切换前验收结果。

页面不得提供直接永久删除旧资料的按钮。永久删除只允许通过本地命令执行，并要求用户再次明确授权。

## 16. 不在本次范围内

- 修改 OA 中的任何事项；
- 重新下载全部历史 OA；
- AI 知识总结、关系提取或知识图谱；
- Curated、Vault、Review、Policy 或治理平台恢复；
- 在线编辑 Markdown；
- 自动删除旧 `data/`；
- 删除 Git 分支、标签、旧代码或旧数据库表。
