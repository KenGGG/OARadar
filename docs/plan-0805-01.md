
## 结论

这个仓库已经具备大约 **80% 的基础能力**：

* 待办：发现、去重、详情抓取、附件下载、解析、LLM 摘要已经存在。
* 已办：增量扫描、附件归档、解析和 Markdown 转换队列已经存在。
* 持久化：SQLite 任务队列、幂等键、失败重试、资源锁已经存在。
* 仍缺：**定时调度、待办摘要到飞书的最后一段、已办归档后自动进入 Markdown 队列，以及目录规范统一。**

因此不建议重写系统，应在现有队列架构上补齐这几处。

# 一、`data` 目录究竟是什么结构

GitHub 仓库看不到你本机真实的 `data/`，因为 `data/`、数据库、日志、浏览器状态和配置文件都被 `.gitignore` 排除了。

## 1. 设计上的目录结构

仓库文档定义的结构是：

```text
data/
├── state/
│   └── oa.db                         # SQLite控制数据库
│
├── archive/
│   └── raw/
│       └── oa/
│           ├── pending/              # 待办原始归档
│           └── done/                 # 已办原始归档
│
├── parse/
│   ├── artifacts/                    # PDF、Word等解析结果
│   ├── staging/                      # 解析临时文件
│   └── failed/                       # 解析失败文件
│
├── runtime/                          # worker锁、运行状态
├── logs/
├── backups/
│
└── workspace/
    ├── raw/
    │   └── sources/
    │       └── oa/
    │           ├── pending/          # 待办Markdown镜像
    │           └── done/             # 已办Markdown镜像
    │
    └── wiki/                         # llm_wiki生成的知识库
```

初始化命令也会建立这些目录；OARadar 负责 `workspace/raw/sources/oa/`，而 `workspace/wiki/`应由 llm_wiki 维护。

## 2. 当前代码存在一个明显的目录不一致

文档和配置规定原始档案放在：

```text
data/archive/raw/oa/
```

但当前 `main` 分支实际写入的是：

```text
data/raw/done/YYYY/MM/事项名称_事项ID/
data/raw/pending/逻辑事项ID/快照ID/
```

已办归档代码直接返回 `raw/done/...`，待办归档代码直接使用 `raw/pending/...`，都没有使用配置中的 `archive/raw/oa`。

因此，你本机现在很可能出现这种情况：

```text
data/
├── archive/raw/oa/        # 初始化创建，可能为空或不完整
├── raw/pending/           # 实际待办数据
├── raw/done/              # 实际已办数据
└── workspace/...
```

这是目前最需要先统一的地方。否则后续备份、知识库导入和目录审计容易混乱。

## 3. SQLite 数据库是整个系统的“控制中枢”

`data/state/oa.db` 并不是简单索引，而是整个工作台的状态机。

主要数据层如下：

```text
OA业务层
├── logical_items          一个事项跨“待办→已办”的统一逻辑身份
├── item_occurrences       待办或已办的具体出现记录
├── item_snapshots         每次抓取形成的不可变快照
├── oa_items               本地归档后的OA事项
└── oa_manifest_items      已办列表的完整清单

文件层
├── files                  本地文件、路径、哈希、下载状态
├── source_attachments     快照与附件之间的关系
├── content_objects        按SHA256去重后的内容对象
├── archive_packages       ZIP等压缩包
└── archive_members        压缩包内部文件

处理层
├── parse_jobs             文档解析任务
├── parse_artifacts        解析产物
├── markdown_tasks         Markdown转换队列
├── markdown_exports       Markdown输出账本
├── summary_jobs           摘要任务
└── summary_versions       待办或已办的摘要版本

运行层
├── operation_jobs         OA扫描、下载等大型任务
├── pipeline_tasks         待办、已办的实时处理队列
├── pipeline_events        各阶段运行记录
├── resource_leases        浏览器、GPU等资源锁
├── notification_deliveries 飞书发送账本
└── review_queue           需要人工处理的异常
```

这些模型说明该系统采用的是“**SQLite保存状态和关系，文件系统保存实际内容**”的架构。

# 二、现有待办流程已经做到哪一步

目前待办的实际链路是：

```text
OA待办列表
  ↓
pending discover
  ↓
item_occurrences
  ↓
比较 discovery_hash
  ↓
仅新增或变化的事项进入 realtime_pending 队列
  ↓
抓取详情、流程意见和附件
  ↓
附件解析
  ↓
本地LLM生成结构化摘要
  ↓
任务完成
```

待办列表已经能取得：

* 标题
* 发起人
* 上一处理人
* 发起时间
* 接收时间
* 截止时间
* 催办次数
* 当前节点
* 重要程度

并以 `pending:<affair_id>` 作为唯一标识。

发现任务后，系统会计算内容哈希。只有新增或内容发生变化时，才会建立新的实时处理任务；原有待办不会每小时重复解析。初始化已有待办时还会设置 `notify=false`，避免第一次部署把全部历史待办推送一遍。

摘要已经包括：

```text
事项摘要
事项类型
发起人
当前阶段
关键要点
需要采取的行动
金额
期限
风险
附件概览
置信度
```

而且会结合已经解析的附件 Markdown，而不只是概括标题。

## 当前真正缺失的环节

worker 在生成待办摘要后直接将任务标记为完成，代码还明确说明“通知发送与抓取流程暂时解耦”。因此，现阶段摘要会保存在 SQLite，但不会自动发到飞书。

目标流程应改成：

```text
pending_summary
  ↓
notify_feishu
  ↓
completed
```

# 三、现有已办流程已经做到哪一步

适合每小时运行的命令已经存在：

```bash
uv run oa manifest refresh-head --max-pages 3 --config config.yaml
```

它只扫描已办列表最新几页，而不是每小时重新遍历全部历史记录。发现新增已办后，会建立下载任务，由后台 worker 抓取详情和附件。

已办文件会按发起时间归档：

```text
raw/done/YYYY/MM/事项标题_事项ID/
├── metadata.json
├── manifest.json
├── body_snapshot/
├── workflow_snapshot/
├── attachments/
└── containers/
```

文件同时记录：

* SHA256
* MIME类型
* 文件大小
* 下载状态
* 附件角色
* 来源容器
* 递归深度

## 已办到知识库之间还差一个稳定触发点

系统已经有：

```python
enqueue_verified_for_oa(...)
```

它可以将已验证附件加入 Markdown 队列。Markdown worker 再转换成：

```text
data/workspace/raw/sources/oa/done/.../*.md
```

但从当前代码看，明确自动调用这个函数的是“全量在线审计”流程。每小时的 `refresh-head → download` 链路不应依赖日后再跑一次全量审计，而应在已办附件成功归档的同一个数据库事务中立即入 Markdown 队列。

应在已办下载成功后增加：

```python
from oa_knowledge.markdown_queue import enqueue_verified_for_oa

queued = enqueue_verified_for_oa(session, row.oa_item_key)
session.commit()
```

这样完整链路才是：

```text
新增已办
  ↓
下载并校验附件
  ↓
原始文件归档
  ↓
加入Markdown队列
  ↓
markdown-worker转换
  ↓
workspace/raw/sources/oa/done
  ↓
llm_wiki监听并生成workspace/wiki
```

# 五、需要修改的代码

## 1. 修复飞书签名

现有 `_sign()` 返回的是十六进制摘要：

```python
hmac.new(...).hexdigest()
```

飞书自定义机器人要求以：

```text
timestamp + "\n" + secret
```

作为 HMAC key，对空字节串计算 HMAC-SHA256，再进行 Base64 编码。现有实现与官方算法不一致。 ([飞书开放平台][1])

应修改为：

```python
def _sign(self, timestamp: int) -> str:
    if not self.secret:
        return ""

    string_to_sign = f"{timestamp}\n{self.secret}"

    digest = hmac.new(
        string_to_sign.encode("utf-8"),
        msg=b"",
        digestmod=hashlib.sha256,
    ).digest()

    return base64.b64encode(digest).decode("utf-8")
```

同时应检查飞书响应 JSON：

```python
result = response.json()
if result.get("code") != 0:
    raise RuntimeError(
        f"Feishu rejected message: {result.get('code')} "
        f"{result.get('msg')}"
    )
```

并同时捕获：

```python
httpx.RequestError
httpx.HTTPStatusError
```

## 2. 增加单个待办摘要卡片

现有 `FeishuNotifier` 偏向“每日汇总”，应增加：

```python
send_pending_summary(summary, occurrence)
```

建议卡片只发送：

```text
标题
发起人
当前节点
简要说明
需要处理的事项
截止时间
主要风险
OA详情链接
```

不发送完整正文和附件内容。

飞书自定义 webhook 只能向它所在的群聊发送，不能直接选择某个个人账号。要实现“发给我”，最简单的是建立一个只有你和机器人的私人群；或者改为飞书应用机器人，通过用户 `open_id` 发送。([飞书开放平台][2])

## 3. 增加通知阶段

在 worker 的任务分派中加入：

```python
elif task.stage == "notify_feishu":
    self._pipeline_notify_feishu(task)
```

修改摘要阶段：

```python
def _pipeline_pending_summary(self, task):
    summary = summarize_pending(
        self.settings,
        self.engine,
        int(task.logical_item_key),
    )

    payload = json.loads(task.payload_json or "{}")

    if payload.get("notify", False):
        self.production_queue.advance(
            task.id,
            self.owner,
            "notify_feishu",
        )
    else:
        self.production_queue.complete(task.id, self.owner)
```

## 4. 使用现有通知账本防止重复推送

仓库已经有 `notification_deliveries` 表，可以直接利用。

幂等键建议为：

```text
feishu:pending:<logical_item_id>:<summary_input_hash>
```

发送前先查询：

```python
existing = session.scalar(
    select(NotificationDelivery).where(
        NotificationDelivery.idempotency_key == idem_key
    )
)
```

状态建议为：

```text
queued
sending
sent
retry_wait
failed
```

这样即使：

* 每小时重复扫描
* worker重启
* 飞书暂时超时
* 同一事项再次入队

也不会重复发送同一版本摘要。

## 5. 已办归档成功后立即入Markdown队列

在 `manifest download` 成功保存附件后调用：

```python
enqueue_verified_for_oa(session, row.oa_item_key)
```

不能只依靠全量在线审计来补队列。

## 6. 统一归档路径

建议最终统一为：

```text
data/archive/raw/oa/pending/
data/archive/raw/oa/done/
```

需要同时修改：

```text
src/oa_knowledge/detail_archive.py
src/oa_knowledge/pending_archive.py
```

并为现有 `data/raw/` 做一次迁移：

1. 暂停两个 worker。
2. 备份 `oa.db`。
3. 移动目录。
4. 更新 `files.local_relpath`、`oa_items.archive_relpath`等字段。
5. 执行完整审计。
6. 恢复 worker。

不要直接用 `mv` 后不更新数据库，否则所有文件索引都会失效。

# 七、Ubuntu 定时运行方案

下面先按广州公司的常规工作时间假定：

```text
周一至周五
09:05、10:05、11:05……17:05
```

使用每小时第5分钟，而不是整点。飞书官方也建议自定义机器人尽量避开整点和半点，以减少限流概率。([飞书开放平台][2])

## 1. 扫描脚本

创建：

```bash
mkdir -p scripts
nano scripts/hourly-sync.sh
```

内容：

```bash
#!/usr/bin/env bash

set -u

cd /实际路径/OARadar || exit 1

CONFIG="/实际路径/OARadar/config.yaml"

pending_status=0
done_status=0

# 扫描全部当前待办。
# 只有新增或变化事项才会进入后续队列。
uv run oa pending discover \
  --limit 500 \
  --max-pages 50 \
  --config "$CONFIG" \
  || pending_status=$?

# 扫描已办最新三页，并为新事项创建归档下载任务。
uv run oa manifest refresh-head \
  --max-pages 3 \
  --config "$CONFIG" \
  || done_status=$?

if (( pending_status != 0 || done_status != 0 )); then
  echo "OARadar hourly scan failed: pending=$pending_status done=$done_status" >&2
  exit 1
fi
```

授权：

```bash
chmod 750 scripts/hourly-sync.sh
```

## 2. OA后台worker

创建：

```ini
# ~/.config/systemd/user/oaradar-worker.service

[Unit]
Description=OARadar OA operation worker

[Service]
Type=simple
WorkingDirectory=/实际路径/OARadar
EnvironmentFile=%h/.config/oaradar/env

Restart=always
RestartSec=5

[Install]
WantedBy=default.target
```

`oa worker` 是现有的持续任务处理命令。

```ini
# ~/.config/systemd/user/oaradar-markdown-worker.service
```

## 4. 每小时扫描服务

```ini
# ~/.config/systemd/user/oaradar-hourly.service

[Unit]
Description=OARadar hourly Pending and Done scan
```

`flock` 可以避免上一次扫描尚未结束时又启动下一次扫描。
