# OARadar 已办同步全链路收敛设计

日期：2026-09-21

## 目标

让所有未被业务规则排除的已办事项，通过同一条可恢复的持久流水线收敛到以下终态之一：

- 已完成：原件已核验，Markdown 正文与事项索引已发布到正确分类目录；
- 无附件：OA 已明确确认没有附件，状态与证据完整；
- 需要处理：下载、解析、分类或发布存在真实且可解释的阻塞。

任何没有实际可执行任务的事项不得显示为“等待下载”或“等待 MD 化”。既有约 2,000 条排除项保持排除，不访问详情、不下载、不转换。

## 当前问题

系统当前存在三类不收敛状态：

1. `pending_download` 事项对应的下载任务已经终态失败，但简化页面仍显示“等待下载”。
2. 一批历史事项已经归档，却没有创建 Markdown 流水线任务，页面长期显示“等待 MD 化”。
3. Markdown 任务已经失败或需要复核，但状态聚合没有稳定地映射为“需要处理”。

此外，已部署 timer 通过本机 drop-in 将仓库中的 23:30 计划覆盖为 06:00，造成配置来源分裂和运行时间误解。

## 方案

### 1. 单一日程来源

仓库内的 systemd timer 模板是唯一日程来源，统一配置为每天 23:30（`Asia/Shanghai`，包含周末）。安装脚本重新渲染 unit 后，不能再依赖机器上的时间覆盖 drop-in。

部署时删除仅包含旧 06:00 时间覆盖的 `daily-0600.conf`，重新加载 user systemd，并验证：

- timer 已启用且处于 waiting；
- 下一次触发是本地时间 23:30；
- service 仍执行完整的 Done 扫描、归档和 Markdown 投递；
- service 结束后常驻 OA worker 自动恢复。

### 2. 可审计的收敛规划器

增加一个本地收敛服务，根据数据库事实为所有未排除事项补齐任务。它只创建或恢复既有持久任务，不直接绕过流水线处理文件。

规划规则：

- `skipped` 或命中排除关键词：保持排除，不建任务。
- 未完成可靠归档的事项：确保存在 `realtime_done / done_capture_and_archive` 任务。
- 已归档但尚未核验：确保任务从 `archive_verify` 继续。
- 原件已核验或明确无附件、但没有完整 Markdown 交付：确保存在 `markdown_delivery` 任务。
- 可恢复失败：重置尝试次数并重新排队，同时写入恢复事件。
- 不可恢复失败、解析不支持、证据不足或需要人工分类：保持终态，显示为“需要处理”，不得循环重试。

任务以现有 idempotency key 和逻辑事项键去重。重复运行规划器必须不产生重复活跃任务。

### 3. 下载与 Markdown 执行

继续使用现有单 OA worker 和持久 `PipelineTask` 队列：

1. OA worker 只读访问 OA，下载详情与附件；
2. 归档写入 `data_root` 下的原件目录并进行完整性校验；
3. 校验成功后创建 Markdown delivery 任务；
4. 解析、分类、正文发布和 `_index.md` 发布按现有阶段推进；
5. 输出路径继续由当前冻结分类决定，位于内部业务分类或外部机构目录下，并按年份分层。

流程保持单浏览器串行，避免并发访问 OA。任务支持重启恢复、租约回收和逐项错误记录。

### 4. 状态口径

简化页面的状态必须同时参考事项事实和最新持久任务：

- 等待下载：存在可执行的 queued/running 下载或归档任务；
- 等待 MD 化：原件已就绪，且存在 queued/running Markdown 任务；
- 需要处理：最新任务终态失败、不可恢复、需要复核、解析不支持或缺少分类证据；
- 已完成：事项索引和所需 Markdown 文件成功发布且账本与文件哈希一致；
- 已排除：命中排除规则；
- 无附件：OA 明确确认无附件，并按既有产品口径展示归档完成状态。

历史事项缺少任务时，收敛规划器运行前可以显示“需要补建任务”；规划器运行后必须转为真实排队或终态，不允许无限期显示模糊“等待”。

## 错误处理与安全

- OA 操作保持只读，不审批、回复、删除、转发或修改任何 OA 记录。
- 容器树最多遍历十层；超过后进入 `depth_limit_reached`，不得标记完成。
- 下载、解析、分类和发布错误分别保存具体错误码与脱敏原因。
- 可恢复错误采用有限重试；达到上限后进入“需要处理”，不无限循环。
- Markdown 发布保持原子写入；已有人工修改或哈希不一致的文件不得覆盖。
- 所有 OA 标识以文本保存；所有归档路径相对 `data_root` 保存。

## 执行与运维

提供一个可重复运行的收敛命令，支持：

- 默认执行：规划缺失任务、恢复可恢复失败并交给 worker；
- dry-run：只输出脱敏计数，不写数据库；
- 状态报告：按下载、归档校验、解析、分类、发布和人工处理汇总数量。

每日 23:30 的完整同步在扫描并创建增量任务后运行一次收敛规划。常驻 worker 在日常时间继续消化队列。

## 验证

自动化测试覆盖：

- 排除项永不建下载或 Markdown 任务；
- 失败下载不会显示为等待下载；
- 缺失 Markdown 任务的历史事项会被补建且重复运行不重复；
- Markdown 失败或待复核显示为需要处理；
- queued/running 任务才显示为等待或处理中；
- timer 模板渲染为每天 23:30；
- worker 交接、租约恢复和任务幂等性。

真实环境验收包括：

- timer 下一次触发时间正确；
- OA worker 与 Markdown worker 正常运行；
- 所有未排除事项不再存在“无任务等待”状态；
- 新生成 Markdown 的数据库记录、实际文件和 SHA-256 一致；
- 剩余未完成事项全部具有明确的活跃任务或“需要处理”原因。

## 非目标

- 不处理或重新分类既有排除项；
- 不改变 OA 端任何数据；
- 不绕过现有分类规则强行发布低质量 Markdown；
- 不把真实失败批量改成成功；
- 不并行启动多个 OA 浏览器 worker。
