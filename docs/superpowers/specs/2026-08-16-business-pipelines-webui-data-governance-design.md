# OARadar 业务流水线、WebUI 与数据治理设计

**日期：** 2026-08-16
**状态：** 用户已批准业务方向，进入实施
**约束：** OA 只读、本地模型、原始已办永久保护、派生数据可重建

## 1. 设计目标

系统围绕两个业务结果组织，而不是围绕下载器、解析器、Markdown 等技术组件组织：

1. 存量已办持续形成完整、可核验、可检索的知识库。
2. 新增或变化的待办及时形成可信摘要并发送飞书，成功后清除临时业务数据。

WebUI、持久任务、状态机和 `data/` 生命周期必须使用同一套业务语义。任何阶段都能回答：当前处理到哪里、为什么停下、能否重试、原件是否安全、派生数据能否重建。

## 2. 数据事实层级

### 2.1 永久保护层

- 已办原始正文、附件、容器树和归档清单；包括 canonical 路径和尚未迁移完成的 legacy 路径。
- 活动 SQLite 数据库、数据库迁移状态、配置、凭据、浏览器登录会话中不可替代的认证数据。
- 最小审计、来源、通知幂等和清理账本。

该层不得被普通清理任务删除。原始已办只能由线上只读核验补齐或标记异常，不自动覆盖、不因重复判断而删除。

### 2.2 忠实 Source Markdown 层

有效 `ParseArtifact` 是唯一可信的机器可读正文来源。它由原始文件确定性解析而来，并记录来源哈希、解析器、配置、质量和版本。

`workspace/raw` 不再单独重新解析原件，而应从有效 `ParseArtifact` 发布可浏览镜像。这样消除 `ParsePipeline` 与 `MarkdownExport` 双重解析造成的内容、引擎和状态漂移。

Source Markdown 必须忠实保留来源元数据、转换说明和解析正文；进入 Curated 编目时，由确定性拆壳器仅提取“文档内容”段。qwen 和最终知识文件不再接收来源提示、转换引擎、转换说明等系统包装。该操作不改写 Source Markdown，规则版本变化会使 Curated 签名失效并安全重建。

### 2.3 可重建投影层

- `workspace/raw`：Source Markdown 的目录镜像；
- `workspace/curated`：经过结构化决策编排的知识目录；
- 旧 `vault`：完成新 Curated 验证后退出；
- 索引、报告、WebUI 聚合视图。

这些内容可删除重建，但删除前必须确认没有活动任务把它们当作唯一输入。

### 2.4 临时层

- 待办正文、附件、解析物和摘要；
- 浏览器 Cache/Code Cache、下载暂存、staging、trace、截图和运行报告；
- 过期数据库备份和迁移快照。

待办临时数据只有在飞书明确 `sent` 后清理；失败和 `unknown_outcome` 必须保留。浏览器缓存可清，但 Cookies、Local Storage、会话和认证数据必须保留。

## 3. 存量已办端到端流水线

```text
定时读取 OA 已办清单
→ 对比本地 manifest 与上次线上观察
→ 新增/变化/不完整项进入下载队列
→ 只读采集正文、附件和关联容器（最多 10 层）
→ 文件类型、大小和 SHA-256 完整性验证
→ 生成/选择有效 ParseArtifact
→ 从 ParseArtifact 发布 Source Markdown 镜像
→ 构建 OA Package
→ 规则去噪 + qwen3.5:9b 结构化分类
→ 发布 Curated 目录
→ 校验、去重和人工复核
```

### 3.1 状态机

每个事项统一映射为以下业务阶段：

- `discovered`：已在线发现；
- `download_pending` / `downloading` / `download_failed`；
- `archive_verified`：所有已识别原件完成本地验证；
- `parse_pending` / `parsing` / `parse_failed` / `source_ready`；
- `curation_pending` / `curating` / `needs_review` / `curation_failed`；
- `published`：Curated 发布且校验通过；
- `depth_limit_reached`：容器树达到 10 层，永远不得视为完整。

阶段由现有事实表计算，不能只依赖一个易漂移的字符串。持久化任务按阶段推进，失败只影响当前事项。

### 3.2 历史全量编目

全量编目创建一个持久化 `OperationJob` 和对应 `PipelineRun/PipelineTask`，不是 Web 请求内同步运行。任务按小批次执行，可暂停、继续、重试和进程重启后恢复。签名未变化的成功项自动跳过；没有原件、有效解析或完整来源边界的事项进入等待/复核，不误报完成。

### 3.3 在线核验、路径收敛与重建门禁

最新一次全量在线核验未完成时，历史重建不得领取任务。核验完成后，Worker 自动创建
`verified_archive_migration` 持久任务，只迁移“完全一致”或“本地合理保留历史资料”且未触发
深度上限的 legacy 已办。迁移前后对完整目录树计算包含相对结构和文件字节的指纹；符号链接、
跨文件系统、目标冲突和指纹变化均停止该事项并进入复核。迁移只使用同文件系统原子改名并
修复数据库引用，不修改历史清单和原件字节。

审计派生的补下载处于排队或执行状态时不得创建迁移任务。补下载成功归档后必须把对应事项
和已结束的审计重新置为待核验，使用新原件重新取证；不得沿用补下载前的“缺失”结论，也
不得在复核完成前迁移目录。

迁移任务确认没有更多安全 legacy 事项后，历史知识队列只保留“canonical 路径 + 最新安全
核验证据”的任务继续执行。核验差异、缺少安全证据或迁移失败对应的排队任务必须转为
不可自动重试的人工复核状态；普通重试和再次启动全量重建均不得重新放行。这里只更新任务
台账和聚合计数，不删除、覆盖或改写原始已办资料。人工处理后，只有后续已完成的全量核验
重新给出安全证据且原件已处于 canonical 路径，迁移收敛阶段才自动解除对应任务门禁，并从
附件清点阶段重新执行，避免沿用复核前的派生状态。

“最新安全核验证据”必须来自数据库中编号最新的核验运行，且该运行状态为已完成。若存在
更新的排队、运行、暂停或重开核验，则更早的已完成运行不得继续授权历史任务，防止在重新
取证窗口内读取陈旧证据。

在线核验按小批次让出唯一 OA Worker；定时待办/已办扫描和实时流水线优先于下一核验批次。
核验抓取必须使用 `online_audit` 的短超时配置，不能复用常规归档的长超时，防止单个大附件
长时间阻塞待办扫描。全部附件和关联容器循环必须实际检查总截止时间；截止后的部分证据
不可用于一致性判断。首轮访问失败自动持久化重试一次，仍失败则进入人工复核，不修改线上
OA，也不覆盖本地原件。

审计总数不是固定快照：定时清单刷新新增的已办必须幂等加入当前运行；已核验事项重新归档
时必须使旧在线证据失效。迁移每批启动前重新确认审计完成；若审计被重开则持久暂停，待其
再次完成后自动恢复。实时待办和实时已办始终优先于路径迁移。

迁移创建还必须验证本次审计时间窗内存在成功的全页清单对账，且页数、线上总数、本地清单
总数和审计分母四者闭合。头部增量刷新不能作为全量覆盖证明。

全页刷新必须更新全部事项的版本签名，并区分新事项、签名变化、失败重试和历史首次基线。
首次基线不触发盲目重下载；新建/变化/失败使用包含签名的幂等键进入实时归档。

迁移任务按 25 项一批断点续跑，开始前暂停旧 Markdown 队列并等待活动读取结束。迁移结束后，
历史队列只领取“canonical 路径且属于最新完成审计安全集合”的事项；路径已经 canonical 但
内容差异、缺件、访问失败或深度异常的事项同样不得领取。差异原件继续冻结，不能因为其余事项开始
重建而被覆盖或删除。WebUI 数据治理页只展示迁移状态、进度、成功、失败和复核聚合数。

首次运行先执行只读预检和 10 条样本。样本通过后才能在 WebUI 明确确认启动全量任务。

## 4. 原始已办线上逐项核验

扩展已有 `OnlineAuditRun/OnlineAuditItem`，而不是建立第二套审计数据库。

### 4.1 核验内容

- 线上事项身份是否存在且唯一；
- OA 已办清单与本地 manifest 的覆盖关系；
- 正文、直接附件、关联附件和容器树数量；
- 本地下载状态、文件大小、哈希与解析覆盖；
- 容器深度是否达到上限；
- 线上新增、本地缺失、本地多出或线上暂时不可访问。

每个事项除整项指纹外，还在本地数据库保存逐附件证据清单：附件角色、文本标识、大小和 SHA-256，不保存第二份线上文件字节。比较器据此区分“完全一致”“附件标识变化”“附件角色变化”“元数据变化但字节一致”“同标识内容变化”和“附件集合变化”。WebUI 只展示原因及数量汇总，逐附件证据留在本地审计账本中。

线上无法提供内容哈希时，只能报告“清单与下载完整性一致”，不能宣称字节完全一致。

### 4.2 核验结果

- `matched`：在线识别集合和本地已验证集合、内容指纹一致；
- `missing_download`：线上识别数大于本地已验证数，已幂等进入补下载；
- `inventory_mismatch` / `content_mismatch`：身份集合或字节内容存在差异，保留证据并进入复核；
- `historical_retained`：本地有线上当前未识别的历史资料，只复核、不删除；
- `content_unverified`：线上未能取得完整字节证据，不能宣称字节一致；
- `access_failed`：登录、权限、超时等访问失败；
- `depth_limit_reached`：需要人工处理更深容器。

任务必须限速、单实例、可暂停续跑、按项提交。补下载只增加或修复本地资料，不修改线上 OA。任何本地“多出”资料都不自动删除。

## 5. 待办端到端流水线

```text
定时读取 OA 待办清单
→ 识别新增或内容变化
→ 临时采集正文、流程证据和附件
→ 生成有效 ParseArtifact
→ qwen3.5:9b 在证据预算内摘要
→ 以内容版本幂等发送飞书
→ sent 后执行数据库关系驱动清理
→ 仅保留最小去重和审计账本
```

清理路径统一解释为相对 `data_root`。旧 `raw/pending/...` 和新 `archive/raw/oa/pending/...` 都必须通过同一个受保护路径解析器。清理先核对投递状态和关系，再删除物理文件，最后删除业务记录；物理删除失败时不得把事项标记为 `cleaned`。`failed`、`retry_wait` 和 `unknown_outcome` 不清理；任何人工或历史兼容的强制参数也不能绕过 `sent` 门禁。普通重试接口拒绝 `unknown_outcome`，WebUI 仅提示人工核对，不显示自动重发和清理操作。

## 6. WebUI 信息架构

一级导航统一为：

1. **总览**：两条业务流水线的结果、积压、失败和需要人工处理的事项。
2. **存量知识**：合并原“已办归档”“Markdown 输出”和 Curated 编目。
3. **待办提醒**：展示发现、下载、MD 化、摘要、飞书、清理六个步骤。
4. **数据治理**：容量、生命周期、审计、清理预检、隔离和恢复。
5. **系统设置**：模型、飞书、调度、服务和高级维护。

### 6.1 存量知识页

- 顶部指标：线上已办总量、本地已发现、原件完整、Source Markdown 就绪、已编目、待复核、失败。
- 事项表：标题搜索及“发现/下载/校验/MD 化/编目/发布”步骤状态。
- 任务区：只读预检、10 条样本、启动全量、暂停、继续、重试失败、校验结果。
- 在线核验区：覆盖率、完全一致、补下载、待复核、访问失败、当前进度和最近核验时间。
- 详情：原件、解析产物、Curated 文档和来源关系；默认不显示敏感正文。

### 6.2 待办提醒页

- 以六步状态条展示每个待办的实际阶段。
- 突出 `unknown_outcome`、摘要失败、飞书失败和清理失败。
- 允许安全重试摘要、明确失败的投递和清理；未知发送结果只能人工确认后处理。

### 6.3 数据治理页

- 按生命周期显示目录容量和文件数量，不展示 OA 标题。
- 展示永久保护、活动、可重建、临时、隔离五类。
- “清理预检”只生成候选和预计释放空间。
- “隔离候选”把可恢复内容原子移动到 `data/quarantine/{运行ID}/`，写入不含正文的清单。
- “恢复”按清单原路恢复且拒绝覆盖；“永久清除”需要隔离期届满和再次确认。
- 单独展示 6 个哈希异常、清单漂移、待办残留和浏览器缓存。

## 7. data 清理策略

### 7.1 可直接清理

仅在浏览器和 Worker 停止时清理 Chrome `Cache`、`Code Cache`、GPU/Dawn Cache；保留 Cookies、Local Storage、IndexedDB、Sessions 和登录状态。删除零字节根目录旧数据库占位文件、明确完成的临时 staging 和标准临时后缀文件前仍需执行路径保护。

### 7.2 先隔离再删除

- 未被数据库和已知事项目录引用的旧待办文件；
- 过期数据库备份（保留最近两份及一份周基线）；
- 运行报告、截图和 trace；
- 新投影验证后退出的旧 `vault`、旧 `workspace/raw` 和失效解析产物；
- 经数据库、清单和线上核验确认不属于任何已办事项的 legacy 残留。

### 7.3 永不由清理器删除

- 任意已办原始文件和其唯一清单；
- 6 个哈希异常及其事项目录；
- 活动数据库/WAL/SHM、凭据和认证状态；
- 活动任务引用的文件；
- 未确认发送成功的待办；
- `depth_limit_reached`、线上无法确认或人工复核中的资料。

## 8. 当前审计基线

- `data/` 约 39GB；原始已办约 33GB。
- 浏览器 `Cache` 和 `Code Cache` 约 1.4GB，是第一批低风险释放对象。
- 数据库备份约 1.1GB，需要建立保留策略。
- 旧 `raw/pending` 中约 29MB 文件没有直接数据库引用，根因是清理路径重复拼接，修复前不删除。
- 约 1.45GB 文件位于数据库已知已办事项目录之外，只能先列为隔离候选。
- 完整性审计发现 6 个 `hash_mismatch` 和 2649 个 `manifest_file_mismatch`；前者冻结保护，后者先区分历史清单格式漂移与真实缺失。

## 9. 错误处理与安全性

- 所有路径先规范化并验证位于 `data_root` 下，拒绝绝对路径、`..`、符号链接逃逸和未解析目标。
- 清理计划带规则版本和文件哈希；执行时重新验证，防止预检后文件变化。
- 原子移动失败不更新数据库状态；跨文件系统移动先复制校验、再切换，但首选同一 `data_root` 内隔离。
- 任务使用租约和心跳；进程死亡后只恢复过期租约。
- 状态/日志只记录 ID、类别、数量、字节和错误码，不输出 OA 正文或完整标题。

## 10. 验证与上线

1. 使用合成数据测试路径、状态机、清理预检/隔离/恢复和持久任务。
2. 修复待办物理清理并验证 legacy/canonical 两种路径。
3. 统一 Source Markdown 发布，验证原件和有效 ParseArtifact 哈希不变。
4. 完成 WebUI/API，再运行前端检查和生产构建。
5. 对真实 `data/` 只运行隐私安全预检；先清低风险缓存，再隔离小样本。
6. 启动 10 条 Curated 样本和小批量在线核验，通过后启动持久化全量任务。
7. 完整运行后端测试、敏感信息检查、迁移、doctor、systemd 和健康检查。

## 11. 回滚

- WebUI/API 可回滚而不影响原始归档。
- Curated、Source Markdown 镜像和旧 vault 都是投影，可按签名重建。
- 隔离内容在永久清除前可以按清单恢复。
- 在线核验和全量编目可暂停；已提交的单项结果保留，恢复后从未完成项继续。
- 任何回滚都不触碰线上 OA。
